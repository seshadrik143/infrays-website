1. What this service is

It's a license issuer that lives at license.infrays.org on a Fly.io machine. One Go binary serves three different audiences over HTTP.

AudienceURL prefixWhat they do
Your customers
People buying NodePulse		 /login, /signup,
/api/portal/*		 Sign up, see their subscriptions / deployments, copy enrollment tokens
Your staff
You, sales, support		 /admin/login,
/api/admin/*		 Onboard customers, issue tokens, revoke licenses, view audit log
The NodePulse server software
Running on the customer's own infrastructure		 /v1/enroll,
/v1/refresh,
/v1/.well-known/keys		 Exchange a token for a signed license, refresh it daily

What it is NOT:

It does NOT host NodePulse itself. NodePulse runs on the customer's own servers. This service only mints + verifies the licenses they need.

3. The 4 actors

Actor 1 — Customer (a paying NodePulse user)

A person who runs NodePulse on their own servers. They never touch the NodePulse source. They just need a license.

What they do:

  • Sign up at license.infrays.org/signup
  • Verify their email
  • Log into license.infrays.org/login (customer portal)
  • See their subscription tier, deployments, enrollment tokens, licenses
  • Copy an enrollment token (one-time shown) and paste it into their NodePulse server config

Actor 2 — Admin (you, sales, support staff)

Someone with infraYS-internal access. Manages customers and licenses.

What they do:

  • Log in at license.infrays.org/admin/login with email + password + TOTP MFA code
  • Create customers, or wait for self-serve via Stripe (when wired)
  • Create offline subscriptions for sales-issued deals
  • Issue enrollment tokens and share them via Slack / password manager
  • Revoke licenses (churn, abuse, etc.)
  • Bulk suspend customers, bulk flag deployments
  • Invite other admins (one-time temp password shown)
  • View audit log (every action is hash-chained)

Actor 3 — NodePulse server software

A running Go binary on the customer's infrastructure. No human at the keyboard.

What it does:

  • Reads license.enrollment_token: NP-ENROLL-XXXX from its config on first start
  • POSTs to license.infrays.org/v1/enroll with the token + a self-generated deployment ID
  • Receives a signed JWS license back, stores it locally
  • Fetches /v1/.well-known/keys to get the public key for verification
  • Every 24h, POSTs to /v1/refresh to get a fresh JWS
  • Reads tier + entitlement limits from the JWS payload
  • Enforces those limits locally
  • Enters "grace" mode if refresh fails for >90 days

Actor 4 — The NodePulse dashboard user

A person inside the customer's organization using NodePulse's own web UI to see metrics, alerts, dashboards.

What they see (regarding licensing):

  • A banner at the top showing license status (active / trial / past-due / expired)
  • An option to enter or update an enrollment token in admin settings
  • Tier-gated features that show or hide based on entitlements in the JWS

They do NOT log into license.infrays.org — that's the customer-portal user (Actor 1), who could be the same person or someone different (procurement, IT lead).

4. End-to-end data flow

This is the one journey that makes the whole system click.

1 Customer signup

Customer visits license.infrays.org/signup

  • POST /api/portal/auth/signup with { email, password, name }
  • Row created in customers table (with bcrypt password hash)
  • Verification token generated, SHA-256 stored as TokenHash
  • Email sent via Postmark with link /verify-email?token=...
2 Customer email verify

Customer clicks link in email

  • POST /api/portal/auth/verify-email with { token }
  • SHA-256(token) matched against TokenHash
  • customers.email_verified_at = now()
3 Customer login

Customer visits /login

  • POST /api/portal/auth/login with { email, password }
  • bcrypt check; account lockout after 5 wrong attempts
  • Session row created in portal_sessions table
  • np_portal_session cookie set (HttpOnly, SameSite=Lax, 7-day TTL)
4 Admin issues subscription + enrollment token

Admin logs in at /admin/login, finds the customer in /admin/customers, clicks into them.

Create subscription:

  • POST /api/admin/customers/{id}/subscriptions with { tier: "professional", current_period_end: <future> }
  • Row in subscriptions table (manual_offline=true, no Stripe ID)

Issue token on that subscription:

  • POST /api/admin/customers/{id}/enrollment-tokens with { subscription_id, label, ttl_hours }
  • Row in enrollment_tokens table (SHA-256 of token stored)
  • Plaintext NP-ENROLL-XXX... shown ONCE in the admin UI
  • Admin copies it, shares via Slack / password manager
5 Customer pastes token into NodePulse server config 
license:
  server_url: https://license.infrays.org
  enrollment_token: NP-ENROLL-XXXXXXXXXXXX

Customer restarts NodePulse server.

6 NodePulse calls /v1/enroll
  • POST https://license.infrays.org/v1/enroll with { enrollment_token, deployment_id, deployment_name, version }
  • Issuer hashes the token, looks up enrollment_tokens row
  • Validates: not expired, not consumed by different deployment
  • Mints a JWS license payload, signed with Ed25519 key
  • Stores licenses row + marks token consumed_at + writes audit log
  • Returns: { license_jws, refresh_at, ... }
7 NodePulse verifies + stores license
  • Calls GET /v1/.well-known/keys (cacheable for ~1 hr)
  • Verifies JWS signature with Ed25519 public key
  • Reads payload: { customer_id, tier, exp, max_agents, ... }
  • Persists the JWS + parsed claims locally
  • Enforces tier limits on all subsequent operations
8 Daily refresh

Every 24h NodePulse calls:

  • POST /v1/refresh with { license_id, deployment_id, version }
  • Issuer mints a NEW JWS (same license_id, new jti)
  • NodePulse rotates its stored JWS

If refresh fails:

  • NodePulse keeps using the cached JWS until expires_at
  • After expires_at, enters grace_until (90 days by default)
  • During grace: read-only mode (no new agents/alerts)
  • After grace: license is fully expired, features lock down

5. Data model in plain English

TableWhat it holds
customersOne row per paying organization. Email, password hash, status (active / suspended / deleted).
subscriptionsOne row per "what tier are they on, when does the period end". Linked to a customer. Stripe subscription ID when self-serve, empty when offline/admin-issued.
enrollment_tokensOne-shot tokens (NP-ENROLL-XXX). Single-use, expire after 24h by default. SHA-256 stored, plaintext shown once.
deploymentsOne row per running NodePulse install. Created when first enrolls. Carries last-seen-at, last-version, flagged-for-review flag.
licensesThe actual JWS records. New row on every refresh (so we audit-trail every license ever issued). Carries jti (unique per issuance), license_id (stable), customer_id, tier, exp, payload_jws.
entitlement_setsThe "what does this tier allow" manifest. free-v1, professional-v1, enterprise-v1. Versioned — when you change tier limits you publish a new version.
admin_usersinfraYS staff. Email, bcrypt hash, role (admin / support / sales / engineer), MFA secret, must_change_password.
portal_sessions / admin_sessionsCookie session rows. Looked up on every authenticated request.
audit_logHash-chained. Every action by an admin or the system writes an entry. Tamper-evident.
webhook_eventsStripe webhook events seen, for idempotent processing.

6. Admin pages walk-through

After you log in at /admin/login and complete the MFA flow:

/admin/dashboard

  • Recent customer count tile
  • Recent customers list (5 most recent)
  • Recent audit events (last 15)
  • Quick links to other pages

/admin/customers

  • Searchable table of all customers (by email or company)
  • Each row: email, company, status, created date
  • Checkboxes for bulk selection → sticky bar appears with Suspend / Reactivate buttons
  • Click any row to drill into customer detail

/admin/customers/{id} — Customer detail

Top: email, name, company, status.

"Account actions" card with Suspend / Reactivate buttons.

Subscriptions section — every subscription this customer has, with "Issue token" button per subscription.

Deployments section — every NodePulse install enrolled by this customer.

  • Per-row Flag / Unflag button + checkbox for bulk flag
  • Bulk action bar appears when ≥1 selected

Enrollment tokens section — every token issued, with Used / Expired / active status.

Licenses section — every JWS ever issued, with Download JWS + Revoke per-row.

One-time secret reveal: When you click "Issue token", a one-time plaintext token (NP-ENROLL-XXX...) appears in a card at the top. Copy it now — it will not be shown again.

/admin/users admin role only

  • Table of every staff admin user (email, role, status, MFA enrollment, last login)
  • Invite admin button — modal with email + role picker → returns a one-time temp password
  • Per-row actions: change role, reset password (new temp shown once), disable, reactivate, delete

Suspending an admin immediately invalidates their active sessions.

/admin/audit

  • Most recent N audit entries (selectable 50 / 100 / 250 / 500)
  • Each row: sequence number, timestamp, event type, actor, customer ID, hash prefix
  • Hash chain is tamper-evident — can be verified via the issuer's audit-verify endpoint

7. How NodePulse connects

The NodePulse dashboard (running on the customer's own server) talks to license.infrays.org only at 3 specific endpoints.

EndpointWhenWhat it does
POST /v1/enroll First start, when customer pastes a fresh token Exchanges token → JWS license
POST /v1/refresh Every 24 hours via a background goroutine Returns new JWS for the same license_id
GET /v1/.well-known/keys On boot + periodically (every ~1 hr) Public-key set for verifying JWS signatures

There is no constant connection — these are HTTP calls every so often. The NodePulse server is otherwise totally independent.

What the NodePulse dashboard UI shows about licensing:

  1. A banner at the top: "Trial expires in N days" / "License active" / "License past due" / "Grace period ends in N days"
  2. In Settings → Licensing: paste an enrollment token, see current tier, see refresh status, see deployment ID
  3. Tier-gated features in the sidebar: features the license doesn't include are visible-but-disabled with an upgrade CTA

The NodePulse dashboard does NOT:

  • Talk to /api/portal/* (those are for customers managing their account on the licensing service)
  • Talk to /api/admin/* (those are for infraYS staff)
  • Have any connection to license.infrays.org beyond the 3 endpoints above

8. Manual end-to-end test plan

Once you've done the 3 operator setup steps (Postgres, admin bootstrap, Postmark approval), here's the manual walkthrough for a tester.

Phase A — Admin onboarding (5 min)

  1. Open https://license.infrays.org/admin/login
  2. Enter the bootstrap admin email + password
  3. Expected: MFA enrollment screen with QR + secret
  4. Scan QR with Google Authenticator (or 1Password / Authy)
  5. Enter the 6-digit code → click "Enable MFA"
  6. Expected: Land on /admin/dashboard with stats tiles (0 customers initially)

Phase B — Customer signup (5 min)

  1. Open a fresh incognito window
  2. Go to https://license.infrays.org/signup
  3. Enter email (must be @infrays.org until Postmark approves external sends), password ≥8 chars, name, company
  4. Expected: "Check your email" screen
  5. Open the inbox in Zoho
  6. Click the "Verify your infraYS account" link
  7. Expected: "Email verified" page, then click "Sign in"
  8. Log in with the credentials
  9. Expected: Customer dashboard with 0 subscriptions, 0 deployments

Phase C — Admin issues subscription + token (5 min)

  1. Back to the admin tab
  2. Refresh /admin/customers — your new test customer should be there
  3. Click on the email to drill into customer detail
  4. Scroll to Subscriptions section — empty
  5. Currently the "Create subscription" button is API-only. From terminal: 
    curl -X POST -b "<your admin cookie>" \
  -H "Content-Type: application/json" \
  -d '{"tier":"professional","current_period_end":"2027-05-22T00:00:00Z"}' \
  https://license.infrays.org/api/admin/customers/<CUSTOMER_ID>/subscriptions
  6. Refresh the customer detail page — subscription appears
  7. Click "Issue token" on that subscription
  8. Modal asks for label + TTL
  9. Expected: A one-time card appears with NP-ENROLL-XXXXXXXX — copy it

Phase D — NodePulse enrollment (10 min)

  1. On a NodePulse-running server, edit config.yaml: 
    license:
  server_url: https://license.infrays.org
  enrollment_token: NP-ENROLL-XXXX...   # from C.9
  2. Restart NodePulse server: systemctl restart nodepulse-server
  3. Check NodePulse logs for license: enrolled successfully, kid=np-fly-2026-01, exp=...
  4. Open the NodePulse dashboard (its own UI, not license.infrays.org)
  5. Settings → Licensing should show: tier=professional, expires=2027-05-22

Phase E — Verify in admin portal (2 min)

  1. Back in /admin/customers/<id>
  2. Deployments section — should now have one row
  3. Enrollment tokens — token shows "Used" with the deployment ID
  4. Licenses — one row showing the issued license, tier=professional

Phase F — Verify refresh (1 hr later, or simulate)

  1. After 24h of NodePulse runtime, NodePulse calls /v1/refresh automatically
  2. Back in /admin/customers/<id> → Licenses: a new row appears (same license_id, new jti)
  3. Audit log at /admin/audit shows license.refreshed event

Phase G — Revocation flow (2 min)

  1. In /admin/customers/<id> → Licenses
  2. Click Revoke on the active license, enter a reason
  3. Expected: badge changes to "Revoked"
  4. Within 24h NodePulse's next refresh receives 403 revoked and enters grace mode
  5. NodePulse dashboard banner changes to: "License revoked — contact support"

Phase H — Bulk operations (2 min)

  1. /admin/customers — select 2+ customers via checkboxes
  2. Click Suspend in the sticky bar → confirm
  3. Expected: Status changes to "suspended" on both rows
  4. Try to log in as one of those customers in incognito — should get "account suspended"

Phase I — Admin user invite (2 min)

  1. /admin/users → Invite admin → enter email + pick role=support
  2. Expected: Card appears with the temp password — copy it
  3. In incognito, log in at /admin/login with that email + temp password
  4. Expected: Forced to change password before anything else
  5. After change-password, forced to enroll MFA
  6. After MFA enrollment → land on dashboard with reduced capabilities (no "Admin Users" tab, etc.)

9. The actual code hook-up to NodePulse

The only code in NodePulse that talks to license.infrays.org is the license client in nodepulse/server/license/client.go. It:

  1. Reads license.enrollment_token and license.server_url from config.yaml
  2. On first start (when no JWS is stored locally), calls POST /v1/enroll
  3. Stores the returned JWS in /var/lib/nodepulse/license.jws (or similar)
  4. Periodically (every 24h) calls POST /v1/refresh
  5. Pulls and caches GET /v1/.well-known/keys for signature verification
  6. The verified payload populates nodepulse/server/featuregate/Gate which the rest of NodePulse uses to gate features

End-to-end inside NodePulse:

nodepulse server starts
  → reads config.yaml (enrollment_token)
  → license client calls license.infrays.org/v1/enroll
  → gets JWS, stores locally
  → loads JWS into featuregate.Gate
  → featuregate.Gate.HasFeature("audit_log") returns true/false per tier
  → API handlers check featuregate.Gate before serving feature endpoints
  → dashboard UI checks gate via /api/v1/billing/features to show/hide UI

The NodePulse dashboard at app.customer-domain.com/nodepulse/dashboard has no idea license.infrays.org exists — it just asks its own NodePulse server "what tier am I?" and the NodePulse server has the JWS payload to answer.
