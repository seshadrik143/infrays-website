Customer Setup · Kubernetes

NodePulse on Kubernetes — Complete Customer Setup Guide

Audience: customer ops / DevOps team installing NodePulse for the first time on their own Kubernetes cluster. Estimated time: 30–45 minutes for a fresh install on an existing cluster.

What you will end up with: a working NodePulse stack inside your Kubernetes cluster (server, dashboard, AI engine, VictoriaMetrics), reachable on your own HTTPS hostname, monitoring Linux hosts and Kubernetes workloads in your environment.
Friendly POC mode (private alpha — current). NodePulse is in private alpha. Three things are temporarily different from the eventual self-serve experience:
  • Signup email must be @infrays.org — Postmark approval is pending, so verification emails to Gmail/Outlook/Yahoo are blocked. Your infraYS contact will provide an @infrays.org alias that forwards to your real inbox.
  • Container images and the agent binary are private. Your infraYS contact will share one read-only GitHub token (read:packages + repo scopes) — used twice: Step 6.1 creates a cluster image-pull secret, Step 10 passes the same value as GITHUB_TOKEN when installing agents on monitored Linux hosts.
  • Manifests are hand-delivered. Your infraYS contact will send you a single nodepulse-k8s.tar.gz bundle over your shared Slack / email — no public download URL during the alpha.
Everything else (the cluster steps, dashboard, agents, billing) is identical to GA. These three friction points disappear at GA cutover.

Prerequisites

Cluster

  • Kubernetes 1.27 or newer (any conformant distribution — EKS, GKE, AKS, K3s, RKE2, OpenShift, on-prem kubeadm).
  • At least 2 vCPU and 4 GB RAM of free capacity on the worker node(s).
  • A default StorageClass able to provision ReadWriteOnce PVCs (gp3, longhorn, OpenEBS, local-path on K3s, …).
  • An Ingress controller already installed (Traefik on K3s ships by default; otherwise install ingress-nginx).

Client machine (where you run kubectl)

  • kubectl ≥ 1.27 configured with cluster-admin context.
  • git (to clone the manifest folder) or just curl + tar.
  • openssl (to generate the secret values you'll rotate in Step 3).

Network

  • Inbound TCP 80 and 443 open to the cluster's Ingress IP / LoadBalancer.
  • One DNS record you control — e.g. nodepulse.yourdomain.com — pointing at the Ingress.
  • Cluster egress to license.infrays.org (licence refresh) and ghcr.io (container image pulls).

Accounts & credentials

  • A NodePulse account on license.infrays.org — created in Step 1, using the @infrays.org address your infraYS contact provides.
  • The manifest bundle (nodepulse-k8s-vX.Y.Z.tar.gz) — delivered by your infraYS contact in Step 2.
  • A GHCR read token (GitHub PAT with read:packages only) — also delivered by your infraYS contact in Step 2. Used once to create an image-pull secret in your cluster.

Pre-handoff checklist (operator-only)

Skip this section if you're the customer following the steps — it's the work your infraYS contact has already done before sending you this guide.

infraYS operator: run this checklist before pointing any customer at this doc. All steps take ~10 minutes total.
  1. Create the customer's @infrays.org alias (or confirm one exists) and verify it forwards to their real inbox. Postmark only delivers to @infrays.org until approval lands.
  2. Cut a tagged manifest bundle from the current main: 
    cd /home/seshu/infrays/Nodepulse
git pull origin main
VERSION=$(git describe --tags --abbrev=0)   # e.g. v0.0.59
tar -czf /tmp/nodepulse-k8s-${VERSION}.tar.gz kubernetes/
echo "Bundle: /tmp/nodepulse-k8s-${VERSION}.tar.gz  (version $VERSION)"
  3. Pin the image tag in the bundle's manifests to the version you cut (vs. a floating sha-*): 
    sed -i "s|:sha-[a-f0-9]\+|:${VERSION}|g" \
  /tmp/staging/kubernetes/server.yaml \
  /tmp/staging/kubernetes/dashboard.yaml \
  /tmp/staging/kubernetes/ai.yaml
    Then re-tar. (Tag ${VERSION} must already exist as a GHCR image — the auto-tag CI publishes these on every push to main.)
  4. Mint a read-only GitHub PAT for the customer:
    • https://github.com/settings/tokens (classic) → Generate new token
    • Note: nodepulse-poc-<customer>-<date>
    • Expiry: 90 days
    • Scopes: read:packages (for GHCR image pulls) + repo (for the private GitHub Release that holds the agent binary). The repo scope is the minimum scope that grants release-asset download on a private repo.
    One token, two uses: Step 6.1 reads it as $GHCR_PAT for the image-pull secret, Step 10 reads the same value as $GITHUB_TOKEN for the agent download.
  5. Send the customer one Slack message containing:
    • The nodepulse-k8s-vX.Y.Z.tar.gz file (drag-drop attachment).
    • The PAT value (and a note: "read:packages scope, 90-day expiry").
    • The customer's signup link: https://license.infrays.org/signup.
    • The @infrays.org alias to sign up with.
    • A link to this guide: https://infrays.org/docs/customer-kubernetes-setup.html.
  6. Stay on standby in the shared channel. The customer's first apply will surface anything subtle in their cluster (storage class, ingress class, etc.). Most installs take 20 minutes; allow 45.

  3. Click the verification link in the email (forwards to your real inbox).
  4. On the dashboard that appears, copy your enrollment token. It looks like: 
    NP-ENROLL-7gK2pQ9xL4mNzR8vY3hT
  5. Save the token in your password manager — you will paste it into a Kubernetes secret in Step 4.

2 Receive the manifest bundle & image-pull token

Your infraYS contact will send you two things in a Slack / email message (see the pre-handoff checklist above):

  1. A file: nodepulse-k8s-vX.Y.Z.tar.gz (the Kubernetes manifests pinned to a tagged version).
  2. A GitHub Personal Access Token, looks like ghp_… (read-only, used once to pull images).

Save the PAT to an env var on the machine where you run kubectl — you'll use it once in Step 6 and then forget about it:

export GHCR_PAT='ghp_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx'   # the value from your infraYS contact
export GHCR_USER='your-github-username'                       # the username it was issued under

Extract the manifests:

tar -xzf nodepulse-k8s-v*.tar.gz
cd kubernetes      # the bundle expands here
ls

You should see:

configmap-agent.yaml
victoriametrics.yaml
ai.yaml

dashboard.yaml

agent-daemonset.yaml      (optional — see Step 11)

Why not just git clone? The NodePulse repo is private during the alpha. Once GA cuts over and images become public, this step will become a single helm install or kubectl apply -f https://… command.

3 Rotate the default secrets

Mandatory. The shipped kubernetes/kustomization.yaml contains placeholder secret values for the quick-start lab. You must replace all three before deploying to anything other than a throwaway VM.

Generate three strong values on your client machine:

JWT_SECRET=$(openssl rand -hex 32)
ADMIN_PWD=$(openssl rand -base64 24 | tr -d '/+=' | head -c 24)
AGENT_KEY="npk_$(openssl rand -hex 24)"

echo "JWT_SECRET     = $JWT_SECRET"
echo "ADMIN_PWD      = $ADMIN_PWD"
echo "AGENT_API_KEY  = $AGENT_KEY"

Store these in your password manager. Then open kubernetes/kustomization.yaml and replace the three literals: values:

secretGenerator:
  - name: nodepulse-runtime-secrets
    literals:
      - NODEPULSE_JWT_SECRET=<paste $JWT_SECRET>
      - NODEPULSE_DEFAULT_ADMIN_PASSWORD=<paste $ADMIN_PWD>
      - NODEPULSE_AGENT_API_KEY=<paste $AGENT_KEY>

The AGENT_API_KEY is the key your external Linux agents will use to send data to the server. Keep it — you'll paste it into each agent's config in Step 10.

4 Paste your enrollment token

The manifests already include the licence wiring (secret → env var → configmap → server). You only need to replace the placeholder token with the value from Step 1.

Open kubernetes/kustomization.yaml and replace this literal:

      - NODEPULSE_ENROLLMENT_TOKEN=REPLACE_WITH_NP-ENROLL-TOKEN_FROM_PORTAL

…with your real token:

      - NODEPULSE_ENROLLMENT_TOKEN=NP-ENROLL-7gK2pQ9xL4mNzR8vY3hT
How the wiring works. The token lives in the Kubernetes Secret (not the ConfigMap, because it's a bearer credential). The server Deployment exposes it as the NODEPULSE_ENROLLMENT_TOKEN env var. The server reads ${NODEPULSE_ENROLLMENT_TOKEN} from the configmap's license.enrollment_token field on boot, swaps in the env value, calls license.infrays.org, caches the signed JWS, and starts.
Don't deploy without replacing the placeholder. If you leave REPLACE_WITH_NP-ENROLL-TOKEN_FROM_PORTAL as-is, the server pod will refuse to start (Phase E2 fail-closed) and crash-loop with a "license required" error.

5 Set your hostname & DNS

Pick the hostname your users will use, e.g. nodepulse.yourcompany.com. Then:

5.1 — Update the ingress

Open kubernetes/ingress.yaml and replace every occurrence of nodepulse.infrays.org with your hostname.

5.2 — Update the server's allowed origins and public URL

In kubernetes/configmap-server.yaml, replace both occurrences of nodepulse.infrays.org:

    security:
      allowed_origins:
        - "https://nodepulse.yourcompany.com"

In kubernetes/server.yaml, replace both occurrences in the env block:

            - name: NODEPULSE_PUBLIC_URL
              value: "https://nodepulse.yourcompany.com"
            - name: NODEPULSE_DASHBOARD_ORIGIN
              value: "https://nodepulse.yourcompany.com"

5.3 — Update the AI engine's CORS origin

In kubernetes/ai.yaml, replace the CORS_ALLOWED_ORIGINS env value:

            - name: CORS_ALLOWED_ORIGINS
              value: "https://nodepulse.yourcompany.com"

If you skip this, AI-engine panels in the dashboard (RCA, anomalies, predictions) will silently fail with CORS errors.

5.4 — Update the in-cluster agent's server URL (only if you'll use Step 11)

In kubernetes/configmap-agent.yaml, replace server_url:

    server_url: "https://nodepulse.yourcompany.com"

Skip this if you're not deploying the optional in-cluster DaemonSet — the configmap will be created but no pod will read it.

5.5 — Sanity check: no nodepulse.infrays.org should remain

grep -rn 'nodepulse\.infrays\.org' kubernetes/
# expected: no output. license.infrays.org is fine — keep it.

5.6 — Point DNS at the ingress

Get your ingress's external address:

kubectl get svc -A | grep -iE 'ingress|traefik'

Create a DNS A record (or CNAME on managed Kubernetes) for nodepulse.yourcompany.com pointing at that address.

6 Create the image-pull secret & apply the manifests

6.1 — Create the namespace and the image-pull secret

The NodePulse container images live in GitHub Container Registry (ghcr.io) and are private during the alpha. You need a docker-registry-type secret in the nodepulse namespace so the cluster can pull them. This is a one-time setup using the PAT from Step 2.

kubectl apply -f kubernetes/namespace.yaml

kubectl -n nodepulse create secret docker-registry ghcr-pull \
  --docker-server=ghcr.io \
  --docker-username="$GHCR_USER" \
  --docker-password="$GHCR_PAT" \
  --docker-email="ops@yourcompany.com"

# Attach the secret to the default service account so all NodePulse
# pods pick it up automatically — no per-deployment edits needed.
kubectl -n nodepulse patch serviceaccount default \
  -p '{"imagePullSecrets":[{"name":"ghcr-pull"}]}'
Why patch the default ServiceAccount? Kubernetes consults the SA's imagePullSecrets when pulling images for any pod that doesn't override it. Patching once means every NodePulse deployment (server, dashboard, AI, agent DaemonSet) authenticates to GHCR automatically.

Once you receive confirmation that GHCR images have been made public (post-GA), this entire sub-step disappears — pods will pull anonymously.

6.2 — Apply everything

kubectl apply -k kubernetes

Expected output:

configmap/nodepulse-server-config created
configmap/nodepulse-agent-config created
secret/nodepulse-runtime-secrets created
service/victoriametrics created

kubectl -n nodepulse run curl --rm -it --image=curlimages/curl --restart=Never -- \

8 First login & change the admin password

  1. Open https://nodepulse.yourcompany.com in your browser (accept the temporary self-signed cert warning if TLS isn't set up yet — Step 9 fixes that).
  2. Log in with username admin and the password you generated in Step 3 ($ADMIN_PWD).
  3. Open Settings → Profile → Change password. Set a strong password and save.
  4. Open Settings → Users. Create a non-admin account for each team member who needs access. Use real names + SSO (Pro/Enterprise tier) where possible.
  5. Open Settings → Licence. Confirm the licence shows your tenant ID, current tier (Trial / Starter / Pro / Enterprise), and expiry.

9 Set up TLS

The shipped ingress works without TLS, but browsers will warn. Pick one of:

Option A — cert-manager + Let's Encrypt (recommended for public clusters)

# Install cert-manager once per cluster
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/latest/download/cert-manager.yaml
kubectl -n cert-manager wait --for=condition=Available deploy --all --timeout=120s

# Create a ClusterIssuer (replace EMAIL)
cat <<EOF | kubectl apply -f -
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: ops@yourcompany.com
    privateKeySecretRef:
      name: letsencrypt-prod-account
    solvers:
      - http01:
          ingress:
            class: nginx        # or traefik, etc.
EOF

Then edit kubernetes/ingress.yaml to add the annotation and TLS block:

metadata:
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
spec:
  tls:
    - hosts:
        - nodepulse.yourcompany.com
      secretName: nodepulse-tls
  rules:
    - host: nodepulse.yourcompany.com
      ...

Re-apply: kubectl apply -k kubernetes. Within a minute or two the cert will be issued and the browser warning disappears.

Option B — bring your own cert

If you already have a wildcard cert or a corporate CA-issued cert:

kubectl -n nodepulse create secret tls nodepulse-tls \
  --cert=path/to/fullchain.pem \
  --key=path/to/private.key

Then reference nodepulse-tls in ingress.yaml as above.

10 Install agents on monitored hosts

Agents run on the Linux servers you want to monitor — not inside the cluster. You install them with a one-line script.

Friendly POC note. During the private alpha, the agent binary lives in a private GitHub release. You'll use the same GHCR_PAT from Step 2 to authenticate the download — pass it as GITHUB_TOKEN. At GA cutover this requirement disappears.

On each monitored host (systemd-based Linux, amd64 or arm64):

# GHCR_PAT is the read-only PAT your infraYS contact gave you in Step 2.
# AGENT_KEY is the value you generated in Step 3.

sudo GITHUB_TOKEN="$GHCR_PAT" bash -c '
  curl -fsSL https://infrays.org/install.sh | bash -s -- \
    --server https://nodepulse.yourcompany.com \
    --key    "'"$AGENT_KEY"'"
'

The installer creates a nodepulse-agent systemd service that pushes metrics, logs, and traces to your server.

Verify the agent appeared in the dashboard:

  1. Open Agents in the dashboard.
  2. You should see the new host within ~30 seconds, marked Online.
  3. Click it to see real-time CPU, memory, disk, network, processes, and logs.
For automation, use Ansible / Terraform / cloud-init to push the install command to fleets. Example Ansible task in docs/guide-agent.html.

11 Optional — Kubernetes-native agent (DaemonSet)

If you also want to monitor the Kubernetes cluster itself (node-level metrics, pod metrics, kubelet, control-plane), deploy the agent as a DaemonSet:

kubectl apply -f kubernetes/agent-daemonset.yaml

One agent pod will be scheduled on every node. They'll appear in Agents alongside your external hosts. The DaemonSet uses the same NODEPULSE_AGENT_API_KEY secret already in the namespace.

Backups

NodePulse stores state in two PVCs in the nodepulse namespace:

  • nodepulse-server-data — users, alert rules, dashboards, incidents, audit log, licence cache.
  • victoriametrics-victoriametrics-0 — all metric history.

Quick option — built-in backup API

curl -fsSL https://nodepulse.yourcompany.com/api/v1/admin/backup \
  -H "Authorization: Bearer <your admin JWT from /api/v1/auth/login>" \
  -o nodepulse-backup-$(date +%F).tar.gz

This produces a single tarball containing all server-side state (BoltDB stores). Schedule it as a Kubernetes CronJob — example in docs/production-deployment.md.

Full option — volume snapshots

For point-in-time restore including metrics, take CSI volume snapshots of both PVCs. Most managed Kubernetes providers (EKS, GKE, AKS) and on-prem CSI drivers (Longhorn, OpenEBS) support this natively.

Upgrades

To upgrade to a newer NodePulse version:

  1. Ask your infraYS contact for the next manifest bundle (e.g. nodepulse-k8s-v0.0.60.tar.gz). They'll send it through the same channel you got the original bundle.
  2. Extract it over your existing copy (your edits to kustomization.yaml — secrets, hostnames, the enrollment token — should be preserved if you only overwrite the YAMLs you didn't customise, OR diff and re-apply your customisations on top).
  3. Re-apply: kubectl apply -k kubernetes.
  4. Watch the rolling update: kubectl -n nodepulse rollout status deploy/nodepulse-server.

Rolling updates are zero-downtime for the dashboard and AI engine. The server has a brief restart while the new pod becomes ready (~10 seconds).

To roll back:

kubectl -n nodepulse rollout undo deploy/nodepulse-server
kubectl -n nodepulse rollout undo deploy/nodepulse-dashboard
kubectl -n nodepulse rollout undo deploy/nodepulse-ai

Uninstall

kubectl delete -k kubernetes
# To also delete the data:
kubectl delete pvc -n nodepulse --all
kubectl delete namespace nodepulse

On monitored hosts, uninstall the agent:

curl -fsSL https://infrays.org/install.sh | sudo bash -s -- --uninstall

Troubleshooting

SymptomLikely causeFix
Server pod CrashLoopBackOff, logs say license required / MustStart failed Placeholder REPLACE_WITH_NP-ENROLL-TOKEN_FROM_PORTAL wasn't replaced in kustomization.yaml, or the real token is invalid/expired Re-check Step 4. Verify the value reached the pod: kubectl -n nodepulse exec deploy/nodepulse-server -- env | grep ENROLL. If it shows the placeholder, edit kustomization.yaml, then kubectl apply -k kubernetes && kubectl -n nodepulse rollout restart deploy/nodepulse-server.
Pods stuck in ImagePullBackOff / ErrImagePull GHCR image-pull secret missing, expired, or PAT lacks read:packages Run kubectl -n nodepulse describe pod <podname> — look for "unauthorized" or "denied". Re-do Step 6.1 with a fresh PAT. Verify the secret: kubectl -n nodepulse get sa default -o yaml | grep -A2 imagePullSecrets.
Server pod runs but logs say license fetch failed: dial tcp … Cluster cannot reach license.infrays.org Check egress firewall / proxy. Allow HTTPS to license.infrays.org. If you use a corporate proxy, set HTTPS_PROXY env on the server deployment.
Server logs say license: deployment_id mismatch The cached JWS was issued for a different deployment Delete the licence cache and restart: kubectl -n nodepulse exec deploy/nodepulse-server -- rm -rf /app/data/license && kubectl -n nodepulse rollout restart deploy/nodepulse-server
VictoriaMetrics pod Pending No default StorageClass kubectl get sc — if empty, install one (longhorn / local-path / your cloud CSI driver).
Ingress 404 Hostname not updated everywhere Re-check Step 5. Grep: grep -r infrays.org kubernetes/ — there should be zero matches if you replaced your hostname correctly.
Dashboard loads, but API calls return 401 Mismatch between NODEPULSE_DASHBOARD_ORIGIN and the URL the browser actually used Both env vars in server.yaml and the allowed-origins list in configmap-server.yaml must match the hostname you typed in the browser.
Agent installed but shows Offline API key mismatch or network egress blocked Compare /etc/nodepulse/agent.yaml on the host with the NODEPULSE_AGENT_API_KEY in the cluster secret. Test reachability: curl -sI https://nodepulse.yourcompany.com/health from the host.
install.sh exits with Could not determine latest version or not a valid ELF binary GITHUB_TOKEN was missing or lacked the repo scope (private-repo asset download requires it) Re-run with the PAT exported: sudo GITHUB_TOKEN="$GHCR_PAT" bash -c 'curl -fsSL https://infrays.org/install.sh | bash -s -- --server … --key …'. If you ran without the token, re-run with it — the script is idempotent.
Browser shows certificate warning TLS not yet configured Step 9. Until then you can dismiss the warning safely on internal networks.
